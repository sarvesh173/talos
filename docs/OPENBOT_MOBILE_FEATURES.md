**Agent/group structure, in one paragraph:** the domain is *servers* (hosts) → *channels/threads* (conversations) → *agents* (each channel bound to one agent, reassignable) → *routines/workflows* (automations attached to agents/channels, with their own runs and approvals) → *connectors* (external chat networks bridged into channels). Agents carry per-agent runtime config (provider, model, reasoning effort), memory/vault data, skills, and files. Live Activities and notifications are per-channel with level/mute control. TALOS's equivalent mapping: server ≈ tailnet host, channel ≈ agent session, agent ≈ one of the 9 CLI agents, routine ≈ cron/watchdog job.

- **KaTeX JS bundled? Yes.** Bundle counts: `katex` ×26, `KaTeX` ×16, including the runtime warning string about KaTeX in quirks mode and separator strings (`katex-newline`, `katex-stretchy`, `katex-smash`, `katex-vbox` in class-name pools). `www.bundle/_expo/static/js/web/katex-7ea67a1cb90b7803eb03a6d736c7b39a.js` (276,281 bytes) is the web chunk.

- **TALOS:** partial — `ui/richtext/LatexSegmenter.kt` segments inline/block maths but no KaTeX-equivalent renderer was found. Adopting proper rendering (WebView KaTeX or a native TeX engine) is **medium** value; segmenting alone gives plain-text maths.

## 6. Notification sounds

Declared in `app.config` (`with-notification-sounds`): 5 files —
`openbot-task.wav`, `openbot-warm.wav`, `openbot-mech.wav`, `openbot-bubble.wav`, `openbot-press.wav`.

The native FCM service (`smali_classes3/run/openbot/mobile/notifications/OpenBotMessagingService.smali`) maps short keys to bundled raw sounds: `task→openbot_task`, `warm→openbot_warm`, `mech→openbot_mech`, `bubble→openbot_bubble`, `press→openbot_press`, plus special values `openbot.sound.none`, `openbot.sound.default`, and a sound prefix `openbot.sound.`. It also reads sealed server config (`push-notifications.json`, HMAC-SHA256).

Bundle settings keys expose user-facing sound choices: `sound.{default,bubble,mech,press,warm}`, `playSound` (test button), `channelSilent`, `mute.{off,for15Minutes,for1Hour,for3Hours,for8Hours,for24Hours,untilTurnedOn}`.

Event → sound mapping is **not stated** anywhere readable (the smali maps keys→files but I did not decode which `kind` values the server sends). Reasonable inference — task = task finished, bubble = new message, mech = agent working, warm = attention needed, press = UI press — is marked as inference, not evidence. There is no per-sound-per-event table in any file I read.

**TALOS:** already better — `NotificationSounds.kt` synthesises a distinct tone sequence per `SoundEvent` at runtime, no WAV assets. Adopt nothing here except the *settings UX*: named sound choices + test-play + per-channel silence + timed mute.

## 8. `www.bundle`

`assets/www.bundle` (73 files, 16,682,714 bytes total) is the **Expo web (DOM component) build**: 7 tiny hashed `.html` shells (~2.8 KB each, `ReactNativeWebView` injection shims — identical except one) + `_expo/static/js/web/` with 66 JS chunks. The largest are app entry chunks (5.68 MB, 2.49 MB, 1.92 MB, …) and three rendering engines: `elk-*.js` (1.53 MB, ELK layout), `katex-*.js` (276 KB), and ~45 Mermaid diagram chunks (`*Diagram-*.js`, `*definition-*.js` — flow, sequence, class, gantt, mindmap, sankey, etc.). ## 9. reasoningEffort

- Exactly **2** occurrences of the literal `reasoningEffort` in the 18.7 MB bundle: (a) an error string `error.agent.reasoningEffort` with message about unsupported Muse protocol version, (b) the i18n key `mobile.agent.runtime.reasoningEffortConfigurable`. No quoted values (`"low"`/`"medium"`/`"high"`/`"xhigh"` = 0 hits each; `"none"` = 6, unrelated pool).
- Neighbouring keys exist: `mobile.agent.runtime.effort`, `...effort.{low,medium,high}` (1 hit each), `effort.xhigh_quality` (1), `minimal` (1). These are i18n key fragments, not value enums — the actual value set lives server-side / in the protocol, not in mobile strings.
- **What it drives:** whether a given agent's model supports configurable reasoning effort at all (`reasoningEffortConfigurable`), surfaced per agent in the runtime picker alongside provider/model. It is a *capability flag + selector*, not an animation parameter.
- **Comparison with TALOS:** TALOS `ReasoningEffortCurve` (`ui/orb/ReasoningEffortOrb.kt`) is the opposite end: six tiers (Off, Low, Medium, High, Max, Ultra — note Max vs OpenBot's xhigh, and Ultra as top step) that drive orb *animation* (intensity, dot count, radius, RGB split, aura density, dwell). TALOS has the presentation layer; OpenBot has the *runtime* layer (does this model accept an effort setting, and which one). The adoptable idea: make effort a per-agent, per-model runtime setting that the orb then visualises — TALOS currently has no evidence of sending effort to the model. **High value** as a feature, low risk (additive).
